## 1. Technical Overview

**MeetSpace** تطبيق ويب تجريبي يعمل محليًا لتقديم حجوزات فعلية لعشر قاعات افتراضية. يختار الموظف هوية تجريبية دون تسجيل دخول، ويطلب الحجز عبر محادثة عربية أو إنجليزية، ثم يرى حجوزاته ويلغيها من قسم مستقل. تعرض لوحة الإدارة جميع الحجوزات وتتيح تغيير حالة القاعة بين «متاحة» و«تحت الصيانة».

**فصل المسؤوليات:** Qwen2 7B يفهم النية، ويستخرج معلومات الطلب، ويساعد في صياغة الحوار. خادم التطبيق وحده يفحص القواعد ويقرر التوفر وينفذ إنشاء/إلغاء الحجز. **إنشاء الحجز عبر المحادثة فقط**؛ لا نموذج حجز يدوي مستقل.

## 2. Technology Stack

| الطبقة | الاختيار | سبب الاختيار |
|---|---|---|
| Frontend | **React + Vite** | واجهة محلية خفيفة بمكونات قليلة؛ لا حاجة لإطار صفحات معقد |
| Backend | **Python + FastAPI** | واجهات API واضحة وسهولة ربط Ollama وFirestore والتحقق من البيانات |
| AI | **Qwen2 7B عبر Ollama محليًا** | قرار BRD معتمد؛ لا API لنموذج خارجي |
| AI integration | **Ollama Chat API** مع Structured JSON Extraction والتحقق البرمجي من الناتج | تقليل الاعتماد على استدعاءات أدوات ينشئها النموذج بحرية |
| Data | **Firebase Firestore** من Backend باستخدام Firebase Admin SDK | حفظ دائم للحجوزات والصيانة مع معاملات ذرية |
| Conversation drafts | ذاكرة مؤقتة في عملية FastAPI | كافية لجلسة العرض؛ لا قاعدة إضافية أو خدمة جلسات |

لا نحتاج LangGraph أو smolagents أو Docker أو استضافة عامة لإكمال MVP؛ يمكن إعادة النظر فقط إذا ظهرت حاجة مثبتة بعد الاختبارات.

## 3. Simple System Architecture

**تدفق الاتصال:**

`المتصفح (React) → FastAPI محلي → (Ollama محلي لفهم النص والردود) + (Firestore سحابي لقراءة القاعات وحفظ الحجوزات)`

- يتصل React بخادم FastAPI على الجهاز نفسه عبر HTTP محلي.
- يتصل FastAPI بواجهة Ollama المحلية لتحليل النص وصياغة رد مناسب.
- يتصل FastAPI بـFirestore باستخدام بيانات اعتماد على الخادم، **ولا يتصل React بـFirestore مباشرة**.
- لا توجد خدمة استضافة ويب عامة. يتطلب Firestore إنترنت، بينما يعمل نموذج اللغة محليًا.
- يتم التحقق النهائي من الشروط والحفظ في الخادم، وليس في المتصفح أو النموذج.

## 4. AI Agent Workflow

1. يختار الموظف من قائمة افتراضية، ثم يبدأ محادثة مرتبطة بهوية ذلك الموظف.
2. يعيد Qwen2 نتيجة منظمة عن **نية الرسالة** والحقول المستخرجة: نوع القاعة، التاريخ، وقت البداية والنهاية، عدد الحضور، ورمز القاعة المختارة إن وُجد.
3. يدمج الخادم الحقول الصالحة مع ما جُمع سابقًا. إذا بقي حقل إلزامي ناقص أو ملتبس، يسأل الوكيل عنه **دون إعادة سؤال عن الحقول المعروفة**.
4. يرفض الخادم القيم غير الصحيحة، ويقرأ القاعات والتوفر الفعلي من Firestore.
5. يعرض الوكيل القاعات المطابقة؛ وعند عدم التوفر يعرض بدائل غير متعارضة، مع توضيح اختلاف نوع القاعة إن تغيّر، ودون اقتراح سعة غير كافية.
6. يختار الموظف أحد الخيارات؛ يحتفظ الخادم بـ**عرض حجز معلّق محدد** مرتبط بـ`session_id` و`employee_id`، ويتضمن القاعة وتاريخ اليوم المحلي وأوقات البداية والنهاية وعدد الحضور. يطلب المساعد تأكيدًا صريحًا.
7. يمكن التأكيد **برسالة طبيعية داخل المحادثة** مثل «أؤكد الحجز» أو «نعم، احجز القاعة»؛ يتعرف المنسّق على نية التأكيد في سياق **عرض معلّق واحد صالح**. العبارة وحدها دون عرض معلّق، أو مع عرض غامض/تغيّر بعد تقديمه، **لا تؤدي إلى إنشاء حجز**؛ بل يطلب المساعد تحديد العرض أو إعادة عرضه.
8. بعد موافقة صريحة على العرض المحدد، يعيد الخادم التحقق من التاريخ والوقت (بما في ذلك شرط اليوم الواحد) والسعة والتوفر والصيانة داخل معاملة Firestore، ويحفظ الحجز إذا بقي صالحًا؛ وإلا يوضح سبب الرفض ويقترح البحث مجددًا.
9. يبني الوكيل رده النهائي على **نتيجة الخادم الفعلية**؛ لا يختلق رقم حجز أو نجاح عملية.

**طريقة الدمج:** لا يُمنح Qwen2 اتصالًا مباشرًا بقاعدة البيانات ولا صلاحية تنفيذ عمليات الكتابة. يُطلب منه JSON منظم عبر Ollama، ويُتحقق منه في Python؛ وتبقى الردود للمستخدم طبيعية وسياقية، بالعربية أو الإنجليزية بحسب المحادثة. إذا تعذر توليد رد طبيعي، يعرض التطبيق رسالة واضحة مستندة إلى حالة العملية الحقيقية.

## 5. Agent Tools & Responsibilities

المقصود بـ«الأدوات» هنا وظائف **الخادم المسموح للمنسق باستدعائها** بناءً على نية المستخدم، وليست أدوات ينفذها النموذج مباشرةً.

| الأداة المنطقية | المسؤولية | ملاحظات |
|---|---|---|
| `extract_booking_request` | استخراج النية والبيانات من المحادثة | Qwen2 ثم تحقق من JSON |
| `find_available_rooms` | قراءة القاعات ومواعيدها والتحقق من المطابقة | قراءة فقط، والفحص النهائي عند التأكيد |
| `suggest_alternatives` | العثور على خيارات صالحة وتوضيح الاختلافات | لا يتجاوز السعة أو الصيانة أو التعارض |
| `confirm_booking` | إعادة فحص القواعد والحفظ | **كتابة فعلية** فقط بعد رسالة تأكيد طبيعية أو إجراء صريح يرتبط بعرض معلّق صالح |
| `list_my_bookings` | إحضار حجوزات الموظف المختار | لقسم «حجوزاتي» |
| `cancel_my_booking` | إلغاء حجز تابع للموظف وتحرير الفترة | من «حجوزاتي»، بعد التحقق من الارتباط بالموظف |
| `list_all_bookings` | عرض كل الحجوزات | للوحة الإدارة التجريبية فقط |
| `set_room_maintenance` | تحديث حالة القاعة | للوحة الإدارة، مع إبقاء الحجوزات السابقة |

لا تتضمن الأدوات إنشاء حجوزات متكررة أو إشعارات أو إجراءات إدارية متقدمة.

## 6. Conversation State Management

- ينشئ FastAPI `session_id` عشوائيًا، مرتبطًا بـ`employee_id`، ويعيده إلى المتصفح.
- يحتفظ أثناء تشغيل الخادم بـ: النية الحالية، الحقول المؤكدة والمفقودة، آخر خيارات القاعات، الخيار المنتظر تأكيده، وعدد محدود من الرسائل السابقة أو ملخصها.
- تُحدث البيانات المستخرجة الجديدة **الحقول المعنية فقط**، ولا تمحو الحقول السابقة ما لم يغيّرها الموظف صراحةً.
- عند اختيار موظف آخر تبدأ جلسة منفصلة؛ لا تنتقل بيانات الطلب غير المكتمل بين الموظفين.
- يحتفظ الخادم بعرض حجز واحد **محدد وصالح ينتظر التأكيد** (`pending_offer`) فيه `offer_id` والقاعة والموعد وعدد الحضور، مرتبط بالجلسة والموظف. التعديل على المعلومات الجوهرية أو تغيير الموظف **يلغي صلاحية العرض السابق** حتى يُعرض خيار محدّث.
- لا يُقبل تأكيد بعبارة طبيعية، أو بأي إجراء آخر، دون وجود العرض المعلّق المحدد المرتبط بالجلسة والموظف نفسه؛ ولا تُعامل الموافقة العامة خارج سياق العرض على أنها أمر تنفيذ.
- **حالة المحادثة مؤقتة:** عند إعادة تشغيل Backend قد تضيع مسودة المحادثة، لكن الحجوزات المؤكدة المحفوظة في Firestore تبقى موجودة.

هذا يلبي سياق المحادثة دون إضافة تخزين دائم لسجل المحادثات غير المطلوب في BRD.

## 7. Firestore Data Structure

| Collection / Document | الحقول الأساسية | الغرض |
|---|---|---|
| `employees/{employee_id}` | `display_name` | موظفون تجريبيون للاختيار، دون كلمات مرور |
| `rooms/{room_id}` | `name`, `type`, `capacity`, `status` | القاعات العشر، و`status`: `available` أو `maintenance` |
| `bookings/{booking_id}` | `employee_id`, `room_id`, `start_at`, `end_at`, `status`, `created_at`, `canceled_at` | سجل دائم، و`status`: `confirmed` أو `canceled` |
| `room_days/{room_id}_{YYYYMMDD}` | `room_id`, `day`, `active_intervals` | سجل تنسيق داخلي لفترات القاعة في **يوم محلي واحد**؛ يضمن منع الحجز المزدوج بمعاملة ذرية |

**ملاحظات البيانات:**
- تُجهّز بيانات القاعات العشر والموظفين الافتراضيين مرة أولى فقط، **دون مسح حجوزات موجودة عند إعادة التشغيل**.
- يُخزن الوقت كتوقيت UTC (Firestore Timestamp)، ويُعرض للمستخدم بتوقيت المشروع المحلي.
- عند إلغاء حجز يبقى المستند في `bookings` بحالة `canceled` ويُزال إشغاله من `active_intervals`.
- `room_days` فهرس تنسيقي **داخلي مشتق** من الحجوزات، وليس وظيفة جديدة للمستخدم أو نوع حجز متكرر. يعتمد `YYYYMMDD` على **التاريخ المحلي بتوقيت Asia/Riyadh**، وإن خُزنت أوقات الحجوزات في UTC.
- **كل حجز يخص يومًا محليًا واحدًا فقط**؛ لذا لا يحتاج حجز واحد إلى تعديل عدة مستندات لأيام متعددة.

## 8. Booking Logic & Validation

**فحص المدخلات:**
1. الحقول اللازمة للحجز: نوع القاعة، التاريخ، وقت البداية، وقت النهاية، وعدد الحضور. اختيار القاعة يتم بعد عرض الخيارات.
2. يجب أن يكون التاريخ والوقت مفهومين وصالحين؛ عند الغموض يسأل المساعد ولا يخمّن. التوقيت المرجعي المعروض للتجربة: **Asia/Riyadh** (افتراض تنفيذي معلن).
3. **`start_at > current_time` عند التنفيذ**: لا حجز في الماضي أو في لحظة مضت.
4. **`end_at > start_at`**، ويجب أن يكون **التاريخ المحلي لبداية الحجز مساويًا للتاريخ المحلي لنهايته بتوقيت Asia/Riyadh**. الحجوزات الممتدة إلى اليوم التالي، بما فيها التي تعبر منتصف الليل، **مرفوضة في MVP**؛ لا يُفسّر وقت نهاية مبكر على أنه في اليوم التالي تلقائيًا. يطلب المساعد وقتًا مصححًا ضمن اليوم نفسه. هذا هو القرار المعتمد **SPEC-01**.
5. عدد الحضور موجب ولا يتجاوز سعة القاعة، ونوع القاعة مناسب (أو نوع بديل بعد بيان الفرق)، وحالة القاعة ليست `maintenance`.
6. يعتبر الموعدان متعارضين إذا كان **بداية الجديد قبل نهاية القائم ونهاية الجديد بعد بداية القائم**؛ التلامس عند الحد فقط مسموح. الحجوزات الملغاة لا تشغل فترة.

**الحفظ ومنع السباق:**
- البحث الأولي للعرض فقط. عند **تأكيد صريح لعرض معلّق صالح** يفحص FastAPI **داخل Firestore Transaction** شروط التاريخ والوقت، وحالة `rooms/{room_id}` وفترات **مستند اليوم المحلي الواحد** `room_days/{room_id}_{YYYYMMDD}`، ثم يحدّث `active_intervals` وينشئ مستند الحجز **في المعاملة نفسها**. لا حاجة إلى التحقق أو الكتابة عبر عدة أيام.
- يقرأ جميع المستندات المطلوبة أولًا قبل أي كتابة داخل المعاملة. إذا سبقت عملية متزامنة وأصبحت الفترة غير متاحة، تُرفض العملية أو تُعاد المعاملة وفق سلوك Firestore، دون حفظ مزدوج.
- يستخدم الخادم معرّفًا/رمز تأكيد فريدًا للطلب لمنع تكرار الحجز عند إعادة إرسال التأكيد؛ لا يتعامل مع تكرار الطلب بوصفه حجزًا جديدًا.
- الإلغاء: يتحقق الخادم من `employee_id` وحالة الحجز، ثم يغيره إلى `canceled` ويزيل فترته من سجلات `room_days` في معاملة واحدة. إعادة طلب إلغاء حجز ملغى لا تعيد إشغاله.
- الصيانة: تحديث `rooms.status` إلى `maintenance` يمنع الحجوزات الجديدة ولا يغير الحجوزات السابقة. يقرأ مسار التأكيد حالة القاعة داخل معاملته، فيتعامل مع تغيّر حالة الصيانة المتزامن.

**مهم:** لا تكفي قراءة قائمة الحجوزات ثم كتابة مستند جديد بصورة منفصلة؛ لا بد من آلية التزامن الذرية أعلاه لضمان منع التعارض الحقيقي.

## 9. Backend APIs

| Method / Path | الوظيفة | المدخلات/النتيجة الأساسية |
|---|---|---|
| `GET /api/employees` | قائمة الموظفين التجريبيين | أسماء ومعرّفات |
| `GET /api/rooms` | القاعات وحالاتها | تفاصيل القاعات العشر |
| `POST /api/chat` | رسالة للمساعد، بما فيها **رسالة تأكيد طبيعية** | `employee_id`, `session_id?`, `message` → رد، بيانات جلسة، خيارات/توضيح؛ عند التأكيد ينفذ الخادم داخليًا `confirm_booking` فقط إذا وجد عرضًا معلّقًا صالحًا وموافقة صريحة |
| `POST /api/bookings/confirm` | تنفيذ تأكيد صريح مرتبط بعرض (إذا استُخدم إجراء تأكيد في الواجهة) | `employee_id`, `session_id`, `offer_id` → نفس قواعد التحقق والحفظ المعتمدة لرسالة التأكيد الطبيعية |
| `GET /api/bookings?employee_id=…` | حجوزاتي | حجوزات الموظف وحالاتها |
| `POST /api/bookings/{id}/cancel` | إلغاء حجز الموظف | `employee_id` → الحالة المحدثة |
| `GET /api/admin/bookings` | كل الحجوزات | بيانات الحجز والموظف والقاعة |
| `PATCH /api/admin/rooms/{id}/status` | تغيير حالة القاعة | `available` أو `maintenance` |

- **لا يُلزم المستخدم بضغط زر لتأكيد الحجز**: جملة طبيعية مثل «أؤكد الحجز» عبر `POST /api/chat` كافية فقط **عندما** يكون العرض المعلّق المحدد صالحًا وتكون موافقته صريحة؛ يستدعي Backend عندها منطق التأكيد ذاته. واجهة `POST /api/bookings/confirm` اختيار تقني لربط إجراء تأكيد صريح إن وُجد، ولا تُنشئ مسار حجز يدويًا منفصلًا.
- تُرفض محاولات التأكيد دون عرض معلّق أو على عرض تغيّرت تفاصيله؛ وحتى مع وجوده تُعاد جميع فحوص الشروط وقت الحفظ.
- تعيد الواجهات أخطاء منظمة وعبارات مفهومة؛ لا تُعد أي استجابة من Qwen2 إثباتًا للحفظ.
- واجهات الإدارة **تجريبية دون مصادقة**؛ تُستخدم محليًا فقط ولا تُنشر للعموم كما هي.

المكونات المشتركة: عرض التحميل، رسالة الخطأ/النجاح، وهوية الموظف المحدد. **لا تصميم بصري، ولا تقويم متقدم، ولا نموذج حجز يدوي** ضمن هذه الوثيقة.

## 11. Error Handling

| الحالة | التصرف الواجب |
|---|---|
| Qwen2/Ollama متوقف أو استجابة غير صالحة | إبلاغ المستخدم بتعذر فهم الرسالة حاليًا وطلب إعادة المحاولة؛ عدم تنفيذ حجز تلقائي |
| بيانات ناقصة أو غامضة | سؤال واحد أو أكثر بحسب النقص، مع الإبقاء على المعلومات الصحيحة |
| تاريخ/وقت غير صالح أو بداية في الماضي أو نهاية غير لاحقة أو نهاية في يوم محلي مختلف | توضيح سبب الرفض وطلب موعد يبدأ وينتهي في اليوم المحلي نفسه |
| لا توجد قاعة مطابقة أو تغيّر التوفر | اقتراح بديل مستوفٍ للشروط أو إيضاح عدم التوفر |
| رسالة تأكيد دون عرض محدد صالح أو بعد تعديل تفاصيله | عدم الحجز؛ طلب اختيار/تأكيد عرض صالح جديد |
| فشل المعاملة/انقطاع Firestore | عدم إعلان نجاح العملية؛ إبلاغ المستخدم بأن الحفظ لم يتأكد، وإتاحة التحقق من «حجوزاتي» قبل إعادة المحاولة |
| إلغاء حجز غير موجود أو غير تابع للموظف أو ملغى أصلًا | رد واضح، دون تعديل حجوزات موظف آخر |
| قاعة تحت الصيانة | عدم إنشاء حجز جديد فيها، مع إبقاء الحجوزات السابقة مسجلة |

لا تُعرض مفاتيح Firebase أو تفاصيل أخطاء الخادم الخام للمستخدم.

## 13. Testing Plan — Typical / Messy / Edge

| الحالة | مدخل الاختبار | التحقق المطلوب |
|---|---|---|
| **Typical** | طلب مكتمل مع قاعة متاحة | استخراج صحيح؛ عرض مطابق؛ تأكيد قبل الحفظ؛ مستند حجز في Firestore؛ ظهوره في «حجوزاتي» |
| **Messy** | طلب ينقصه عدد الحضور أو وقت النهاية مثلًا | يسأل عن الناقص فقط؛ يحتفظ ببقية المعلومات؛ لا حجز قبل اكتمال البيانات والتأكيد |
| **Edge** | طلب وقت مشغول بحجز سابق | يكتشف التعارض الفعلي؛ لا ينشئ حجزًا متعارضًا؛ يقترح خيارات مناسبة |

**فحوص جاهزية مساندة وغير محسوبة كتجارب تقييم إضافية:** إعادة تشغيل التطبيق والتحقق من بقاء الحجز، إلغاء الحجز وتحرير وقته، تغيير الموظف واختلاف قائمة «حجوزاتي»، منع القاعة تحت الصيانة، رفض الماضي ونهاية الوقت غير الصحيحة **ورفض أي حجز يمتد إلى اليوم التالي**، تأكيد طبيعي صالح برسالة «أؤكد الحجز» ورفض التأكيد دون عرض معلّق، ومحاولة تأكيدين متزامنين للقاعة والفترة نفسيهما.

**قياس الإنتاجية:** تنفيذ تجربتين مقاستين على الأقل مقارنةً بمسار البريد + Excel، مع تسجيل زمن العمل الفعلي والمدة الإجمالية إن لزم وصحة النتائج والأخطاء/التصحيحات. لا توضع أرقام أو نسب قبل القياس الفعلي. يُوثّق استخدام RICE وتعديلات التعليمات ونتائج التحسين في مرحلة التقييم المخصصة.

## 14. Technical Constraints & Assumptions

- **معتمد:** تشغيل الواجهة والخادم وQwen2 7B عبر Ollama **محليًا**؛ Firestore **سحابي** يتطلب اتصال إنترنت؛ لا استضافة عامة حاليًا.
- **معتمد:** بيانات افتراضية، 10 قاعات، اختيار موظف دون تسجيل دخول، ولوحة إدارة بسيطة لا تُعد نظام صلاحيات.
- **معتمد (SPEC-01):** حجوزات اليوم الواحد فقط وفق `Asia/Riyadh`؛ يمنع عبر منتصف الليل أو إلى اليوم التالي. لا توجد حجوزات متعددة الأيام أو متكررة.
- **افتراض تنفيذي للمراجعة:** المنطقة الزمنية للمواعيد المعروضة **Asia/Riyadh**؛ تخزين timestamps في UTC. أي تاريخ غير محدد أو ملتبس يستلزم توضيحًا لا تخمينًا.
- **افتراض تنفيذي:** تشغيل Backend كعملية محلية واحدة؛ سياق المحادثة غير دائم، بعكس الحجوزات والتغييرات المحفوظة في Firestore.
- يجب إعداد مشروع Firebase وبيانات اعتماد خاصة بالخادم وضبط اتصال Ollama مسبقًا؛ لا تُضمّن الأسرار في React أو الملفات المنشورة.
- لا تُستخدم بيانات حقيقية أو أسرار في العرض، ولا تُعتبر واجهات الإدارة المحمية فقط بإخفائها من الشاشة آمنة للنشر العام.
- تغيير التقنية، إضافة استضافة، أو إدخال ميزات خارج BRD يتطلب قرارًا جديدًا من صاحبة المشروع.
- تستند طريقة المعاملات الذرية وإعادة المحاولة إلى توثيق Firestore الرسمي، واستخراج JSON المنظم إلى واجهة Ollama الرسمية:
  - [Firebase: Transactions and batched writes](https://firebase.google.com/docs/firestore/manage-data/transactions)
  - [Ollama: Structured outputs](https://ollama.com/blog/structured-outputs)
